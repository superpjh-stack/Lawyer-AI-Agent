# LexAgent v0.7 - RAG + LangChain.js Architecture Design

> Phase: Design | Feature: RAG AI System | Date: 2026-03-09

---

## 1. Executive Summary

v0.7 introduces a **Retrieval-Augmented Generation (RAG)** system powered by **LangChain.js** and **pgvector**, replacing the current direct OpenAI orchestrator (`orchestrator.ts`). Key capabilities:

- Document upload and vector embedding for law-firm knowledge
- Per-lawyer personalization via metadata-filtered retrieval
- Enhanced `/chat` and `/advisory` pages with RAG-grounded responses
- Conversation memory with LangChain's buffer/summary patterns

### Scope Boundary

| In Scope | Out of Scope (v0.8+) |
|----------|----------------------|
| pgvector extension on GCP Cloud SQL | Supabase Storage file upload |
| LangChain.js RAG chain for chat/advisory | Redis caching layer |
| Per-lawyer namespace filtering | Resend email notifications |
| Document embedding pipeline | Multi-tenant firm isolation |
| Source citation in responses | Fine-tuning / custom model training |

## 2. Current State Analysis

### 2.1 Existing AI Pipeline

```
User Message
  -> orchestratorAgent.run()
     -> OpenAI GPT-4o (direct API call)
     -> Tool calls: search_laws, search_cases, analyze_document, draft_document, manage_deadline, search_documents
     -> SSE streaming response
```

**Problems with current approach:**
1. `search_documents` is a mock -- returns hardcoded data
2. `analyze_document` is a mock -- no real document analysis
3. No vector search -- cannot find similar documents semantically
4. No per-lawyer personalization
5. No conversation memory beyond last 10 messages from DB
6. Advisory agent has no access to firm's knowledge base

### 2.2 Key Files to Modify

## 3. Architecture Design

### 3.1 High-Level RAG Flow

```
[Lawyer uploads document]
  -> Text extraction (PDF/DOCX/TXT)
  -> Text splitting (RecursiveCharacterTextSplitter, 1000 chars, 200 overlap)
  -> OpenAI text-embedding-3-small (1536 dimensions)
  -> Store in PostgreSQL via pgvector (LawKnowledge table)
  -> Metadata: { lawyerId, docType, practiceArea, sourceDocumentId }

[User asks question in /chat]
  -> LangChain createHistoryAwareRetriever
     -> Reformulate question with chat history context
  -> PGVectorStore.similaritySearch(query, k=5, filter={lawyerId})
  -> Retrieved chunks injected as context
  -> GPT-4o generates answer with source citations
  -> SSE streaming to client
```

### 3.2 Component Architecture

```
src/lib/
  rag/
    index.ts              -- Public API: createRAGChain, embedDocument
    vectorstore.ts        -- PGVectorStore singleton factory
    embeddings.ts         -- OpenAI embeddings wrapper
    splitter.ts           -- Text splitting configuration
    retriever.ts          -- Metadata-filtered retriever factory
    chains/
      chat-rag.ts         -- Chat RAG chain (replaces orchestrator for RAG queries)
      advisory-rag.ts     -- Advisory RAG chain (context injection)
    memory/
      conversation.ts     -- LangChain conversation memory (DB-backed)
    ingest/
      pipeline.ts         -- Document ingestion pipeline
      extractors.ts       -- PDF/DOCX/TXT text extraction
```

### 3.3 Integration Pattern: Gradual Replacement

The orchestrator is NOT deleted. Instead, a **RAG-enhanced wrapper** is placed in front:

```
User Question
  -> RAGOrchestrator (new)
     -> Step 1: Retrieve relevant context from PGVectorStore
     -> Step 2: Augment system prompt with retrieved context
     -> Step 3: Delegate to existing OrchestratorAgent (tool-use loop)
     -> Tools still work (search_laws, search_cases, etc.)
     -> But now search_documents uses REAL vector search
```

This preserves all existing tool functionality while adding RAG grounding.

```typescript
import { PGVectorStore } from "@langchain/community/vectorstores/pgvector";
import { OpenAIEmbeddings } from "@langchain/openai";
import { PoolConfig } from "pg";

const EMBEDDING_MODEL = "text-embedding-3-small"; // 1536 dimensions
const COLLECTION_NAME = "law_knowledge";

export function getEmbeddings(): OpenAIEmbeddings {
  return new OpenAIEmbeddings({
    modelName: EMBEDDING_MODEL,
    openAIApiKey: process.env.OPENAI_API_KEY,
  });
}

export async function getVectorStore(): Promise<PGVectorStore> {
  const pgConfig: PoolConfig = {
    connectionString: process.env.DATABASE_URL,
  };

  return PGVectorStore.initialize(getEmbeddings(), {
    postgresConnectionOptions: pgConfig,
    tableName: "LawKnowledge",
    columns: {
      idColumnName: "id",
      vectorColumnName: "embedding",
      contentColumnName: "content",
      metadataColumnName: "metadata",
    },
    distanceStrategy: "cosine",
  });
}
```

### 5.3 Metadata-Filtered Retriever

```typescript
// src/lib/rag/retriever.ts
import { VectorStoreRetriever } from "@langchain/core/vectorstores";
import { getVectorStore } from "./vectorstore";

export interface RetrieverOptions {
  lawyerId: string;
  docType?: string;
  practiceArea?: string;
  k?: number; // number of results, default 5
}

export async function createFilteredRetriever(
  options: RetrieverOptions
): Promise<VectorStoreRetriever> {
  const vectorStore = await getVectorStore();

  // Build metadata filter
  const filter: Record<string, unknown> = {};
  // Include both personal AND shared knowledge (lawyerId = null)
  // PGVectorStore supports $or style filters
  if (options.lawyerId) {
    filter["$or"] = [
      { lawyerId: options.lawyerId },
      { lawyerId: null }, // shared knowledge
    ];
  }
  if (options.docType) filter.docType = options.docType;
  if (options.practiceArea) filter.practiceArea = options.practiceArea;

  return vectorStore.asRetriever({
    k: options.k ?? 5,
    filter,
  });
}
```

```typescript
1. 정확한 법률 정보 제공 (불확실한 경우 "확인 필요" 표시)
2. 판례/법령 인용 시 출처 명시

4. 컨텍스트에서 참고한 문서가 있으면 [출처: 문서명] 형태로 표시

{context}`;

const QA_PROMPT = ChatPromptTemplate.fromMessages([
  ["system", QA_SYSTEM_PROMPT],
  new MessagesPlaceholder("chat_history"),
  ["human", "{input}"],
]);

export async function createChatRAGChain(lawyerId: string) {
  const llm = new ChatOpenAI({
    modelName: "gpt-4o",
    temperature: 0.3,
    streaming: true,
    openAIApiKey: process.env.OPENAI_API_KEY,
  });

  const retriever = await createFilteredRetriever({ lawyerId, k: 5 });

  const historyAwareRetriever = await createHistoryAwareRetriever({
    llm,
    retriever,
    rephrasePrompt: CONTEXTUALIZE_PROMPT,
  });

  const questionAnswerChain = await createStuffDocumentsChain({
    llm,
    prompt: QA_PROMPT,
  });

  return createRetrievalChain({
    retriever: historyAwareRetriever,
    combineDocsChain: questionAnswerChain,
  });
}

// Convert DB messages to LangChain format
export function toBaseMessages(
  history: Array<{ role: string; content: string }>
): BaseMessage[] {
  return history.map((m) =>
    m.role === "user" ? new HumanMessage(m.content) : new AIMessage(m.content)
  );
}
```

### 5.5 Conversation Memory (DB-Backed)

```typescript
// src/lib/rag/memory/conversation.ts
import { BufferWindowMemory } from "langchain/memory";
import { prisma } from "@/lib/db/prisma";

// We use a simple approach: load last N messages from DB
// rather than LangChain's built-in memory stores,
// because we already persist messages in PostgreSQL.

export async function loadConversationHistory(
  conversationId: string,
  windowSize: number = 10
): Promise<Array<{ role: "user" | "assistant"; content: string }>> {
  const messages = await prisma.message.findMany({
    where: { conversationId },
    orderBy: { createdAt: "asc" },
    take: windowSize,
    select: { role: true, content: true },
  });

  return messages.map((m) => ({
    role: m.role as "user" | "assistant",
    content: m.content,
  }));
}
```

### 5.6 Document Ingestion Pipeline

```typescript
// src/lib/rag/ingest/pipeline.ts
import { RecursiveCharacterTextSplitter } from "langchain/text_splitter";
import { getVectorStore, getEmbeddings } from "../vectorstore";
import { prisma } from "@/lib/db/prisma";
import { extractText } from "./extractors";

const splitter = new RecursiveCharacterTextSplitter({
  chunkSize: 1000,
  chunkOverlap: 200,
  separators: ["\n\n", "\n", ".", " "],
});

export interface IngestOptions {
  documentId: string;    // Document.id from Prisma
  lawyerId: string;
  docType: string;       // form | procedure | sentence_style | precedent | ...
  practiceArea: string;  // civil | criminal | corporate | ...
  title: string;
  fileUrl: string;
  mimeType: string;
}

export async function ingestDocument(options: IngestOptions): Promise<{
  chunksCreated: number;
  success: boolean;
}> {
  try {
    // 1. Update status to processing
    await prisma.document.update({
      where: { id: options.documentId },
      data: { embeddingStatus: "processing" },
    });

    // 2. Extract text from file
    const rawText = await extractText(options.fileUrl, options.mimeType);

    // 3. Split into chunks
    const chunks = await splitter.splitText(rawText);

    // 4. Store in vector store
    const vectorStore = await getVectorStore();

    const documents = chunks.map((chunk, index) => ({
      pageContent: chunk,
      metadata: {
        lawyerId: options.lawyerId,
        sourceDocId: options.documentId,
        docType: options.docType,
        practiceArea: options.practiceArea,
        title: options.title,
        chunkIndex: index,
      },
    }));

    await vectorStore.addDocuments(documents);

    // 5. Update status to completed
    await prisma.document.update({
      where: { id: options.documentId },
      data: { embeddingStatus: "completed" },
    });

    return { chunksCreated: chunks.length, success: true };
  } catch (error) {
    console.error("[ingest] Error:", error);
    await prisma.document.update({
      where: { id: options.documentId },
      data: { embeddingStatus: "failed" },
    });
    return { chunksCreated: 0, success: false };
  }
}
```

### 5.7 Text Extractors

```typescript
// src/lib/rag/ingest/extractors.ts

export async function extractText(fileUrl: string, mimeType: string): Promise<string> {
  // For v0.7, support plain text and PDF
  if (mimeType === "text/plain") {
    const response = await fetch(fileUrl);
    return response.text();
  }

  if (mimeType === "application/pdf") {
    const pdfParse = await import("pdf-parse");
    const response = await fetch(fileUrl);
    const buffer = Buffer.from(await response.arrayBuffer());
    const data = await pdfParse.default(buffer);
    return data.text;
  }

  if (mimeType === "application/vnd.openxmlformats-officedocument.wordprocessingml.document") {
    // DOCX: extract raw text (simple approach for v0.7)
    // Full DOCX parsing can be added in v0.8
    const response = await fetch(fileUrl);
    const buffer = Buffer.from(await response.arrayBuffer());
    // Use the 'docx' package already in dependencies for basic extraction
    return `[DOCX document - text extraction pending full implementation]`;
  }

  throw new Error(`Unsupported mime type for text extraction: ${mimeType}`);
}
```

## 6. Per-Lawyer Personalization System

### 6.1 How It Works

Each lawyer has their own "knowledge space" in the vector store, separated by `lawyerId` metadata:

```
[Shared Knowledge (lawyerId = null)]
  - Common law articles
  - Standard templates
  - Public precedents

[Lawyer A's Knowledge]
  - Their own contract templates
  - Preferred sentence styles
  - Frequently referenced precedents
  - Practice area specialization

[Lawyer B's Knowledge]
  - Different templates
  - Different style preferences
```

### 6.2 Document Types for Personalization

| docType | Purpose | Example |
|---------|---------|---------|
| `form` | Document templates | Contract forms, complaint templates |
| `procedure` | Legal procedures | Divorce procedure steps, IP filing |
| `sentence_style` | Writing style samples | Lawyer's preferred phrasing |
| `precedent` | Case precedents | Important rulings for reference |
| `contract` | Contract samples | Standard agreements used |
| `law_article` | Statute articles | Key law provisions |

### 6.3 Practice Areas

| Code | Korean | Description |
|------|--------|-------------|
| `civil` | 민사 | Civil law |
| `criminal` | 형사 | Criminal law |
| `corporate` | 기업/상사 | Corporate/Commercial |
| `family` | 가사 | Family law |
| `real_estate` | 부동산 | Real estate |
| `labor` | 노동 | Labor/Employment |
| `ip` | 지식재산 | Intellectual property |
| `administrative` | 행정 | Administrative |
| `general` | 일반 | General |

### 6.4 Retrieval Strategy

When a lawyer asks a question:
1. Query embedding is computed
2. PGVectorStore searches with filter: `lawyerId = currentUser OR lawyerId IS NULL`
3. Results are ranked by cosine similarity
4. Top-K (default 5) chunks are injected into the LLM context
5. LLM generates response citing sources

## 12. Security Considerations

1. **Data Isolation**: Lawyers can only search their own + shared knowledge (enforced by metadata filter)
2. **Upload Validation**: File size limits, mime type validation before embedding
3. **Rate Limiting**: Embedding requests rate-limited (expensive API calls)
4. **Prompt Injection**: RAG context is clearly delimited in system prompt
5. **No PII in Embeddings**: Embedding vectors are not reversible to original text, but the stored `content` field contains the text -- access controlled via auth
