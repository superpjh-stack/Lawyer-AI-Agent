## 1. Overview

### 1.1 Design Goals

1. **v0.7 설계 계승**: 기존 v0.7 RAG 아키텍처를 기반으로 5대 고급 기능까지 확장
2. **점진적 교체**: 기존 orchestrator를 삭제하지 않고 RAG 래퍼로 감싸는 방식 유지
3. **모듈화**: 각 기능이 독립적으로 동작하되 공유 RAG 인프라 활용
4. **한국어 법률 도메인 최적화**: 청크 분할, 프롬프트, 검색 전략 모두 한국어 법률에 맞춤

### 1.2 Design Principles

- **Single Responsibility**: 각 RAG 컴포넌트는 하나의 역할만 담당
- **Open-Closed**: 새로운 문서 타입/분석 체인 추가 시 기존 코드 수정 불필요
- **Dependency Inversion**: 비즈니스 로직은 벡터 스토어 구현에 의존하지 않음

## 2. Current State Analysis

### 2.1 Existing Architecture (v0.8)

```
User Message
  -> POST /api/chat (SSE)
     -> OrchestratorAgent.run()
        -> OpenAI GPT-4o (tool_calls loop)
        -> Tools:
           [real] search_laws (국가법령정보 API)
           [real] search_cases (국가법령정보 API)
           [real] manage_deadline (Prisma DB)
           [MOCK] analyze_document (hardcoded)
           [MOCK] draft_document (hardcoded)
           [MOCK] search_documents (hardcoded)
        -> SSE streaming response
```

### 2.2 v0.9 Target Architecture

```
User Message
  -> POST /api/chat (SSE)
     -> RAGOrchestrator (new wrapper)
        -> Step 1: Retrieve context from PGVectorStore (LawKnowledge)
        -> Step 2: Augment system prompt with retrieved context
        -> Step 3: Delegate to OrchestratorAgent (existing)
           -> Tools (all REAL now):
              [real] search_laws (국가법령정보 API)
              [real] search_cases (국가법령정보 API + Vector Hybrid)
              [real] manage_deadline (Prisma DB)
              [REAL] analyze_document (RAG + risk chain)
              [REAL] draft_document (RAG + draft chain)
              [REAL] search_documents (pgvector similarity search)
        -> SSE streaming with source citations
```

## 4. Database Schema Changes

### 4.1 New Model: LawKnowledge

Inherited from v0.7 design with minor additions.

```prisma
model LawKnowledge {
  id             String   @id @default(cuid())
  lawyerId       String?  // null = shared/public knowledge
  sourceDocId    String?  // reference to Document.id if from upload
  title          String
  content        String   // chunk text content
  chunkIndex     Int      @default(0)
  totalChunks    Int      @default(1)  // [NEW] total chunks in source doc
  docType        String   // form | procedure | sentence_style | precedent | contract | law_article
  practiceArea   String   // civil | criminal | corporate | family | real_estate | labor | ip | administrative | general
  metadata       Json?    // flexible extra metadata
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  lawyer         User?     @relation("LawyerKnowledge", fields: [lawyerId], references: [id])
  sourceDocument Document? @relation("KnowledgeSource", fields: [sourceDocId], references: [id])

  @@index([lawyerId])
  @@index([docType])
  @@index([practiceArea])
  @@index([lawyerId, docType])
  @@index([lawyerId, practiceArea])
}
```

```typescript
export interface HybridSearchOptions {
  query: string;
  lawyerId?: string;
  k?: number;          // final result count (default 10)
  vectorWeight?: number; // 0.0 - 1.0 (default 0.6)
  bm25Weight?: number;   // 0.0 - 1.0 (default 0.4)
  mode: 'keyword' | 'semantic' | 'hybrid';
}

export interface HybridSearchResult {
  id: string;
  content: string;
  score: number;        // RRF combined score
  source: 'vector' | 'bm25' | 'both';
  metadata: Record<string, unknown>;
}

// Implementation:
// 1. If mode=keyword: BM25 only (existing API search)
// 2. If mode=semantic: pgvector cosine similarity only
// 3. If mode=hybrid:
//    a. Run both searches in parallel
//    b. Apply Reciprocal Rank Fusion (RRF):
//       score(d) = sum( 1 / (k + rank_i(d)) ) for each ranker i
//       where k = 60 (standard RRF constant)
//    c. Return top-k merged results
```

## 6. RAG Orchestrator Integration

### 6.1 RAGOrchestrator Wrapper

The key integration point: wraps the existing OrchestratorAgent to inject RAG context.

```typescript
// src/lib/rag/index.ts (main entry point)

export class RAGOrchestrator {
  private orchestrator: OrchestratorAgent;
  private enabled: boolean;

  constructor(options: { enabled?: boolean }) {
    this.orchestrator = new OrchestratorAgent();
    this.enabled = options.enabled ?? true;
  }

  async run(options: OrchestratorRunOptions): Promise<OrchestratorResult> {
    if (!this.enabled) {
      // Bypass RAG, use plain orchestrator
      return this.orchestrator.run(options);
    }

    // 1. Retrieve relevant context
    const retriever = await createFilteredRetriever({
      lawyerId: options.userId,
      k: 5
    });
    const docs = await retriever.getRelevantDocuments(options.userMessage);

    // 2. Build augmented system prompt
    const contextBlock = docs.map((d, i) =>
      `[참조 ${i+1}: ${d.metadata.title ?? '문서'}]\n${d.pageContent}`
    ).join('\n\n');

    // 3. Inject context into conversation
    const augmentedHistory = [
      {
        role: 'system' as const,
        content: `## 참조 문서 (지식베이스에서 검색됨)\n${contextBlock}`
      },
      ...options.conversationHistory
    ];

    // 4. Replace mock tools with real implementations
    // This is done at the OrchestratorAgent level (modified tools)

    return this.orchestrator.run({
      ...options,
      conversationHistory: augmentedHistory
    });
  }
}
```

## 7. Ingestion Pipeline Design

### 7.1 Single Document Flow

```
Upload Request
  -> Validate (size <= 20MB, MIME whitelist)
  -> Store file (local/GCS)
  -> Create Document record (Prisma)
  -> Set embeddingStatus = "processing"
  -> Extract text:
     PDF  -> pdf-parse
     DOCX -> mammoth.js (extractRawText)
     TXT  -> direct read
  -> Split text (RecursiveCharacterTextSplitter, 1000/200)
  -> Generate embeddings (OpenAI, batch of chunks)
  -> Store in LawKnowledge table (Prisma + raw SQL for vector)
  -> Set embeddingStatus = "completed"
  -> Return { chunksCreated, success }
```

### 7.2 Batch Upload Flow

```
Batch Upload (up to 20 files)
  -> Validate each file
  -> Create all Document records
  -> Queue each for async ingestion
  -> Return immediately with job IDs
  -> Process sequentially (avoid API rate limits)
  -> SSE or polling for progress updates
```

### 7.3 Error Handling

| Error | Handling |
|-------|---------|
| PDF parsing fails | Set embeddingStatus = "failed", log error, notify user |
| OpenAI embedding rate limit | Exponential backoff, retry up to 3 times |
| Database write fails | Rollback LawKnowledge entries, set status = "failed" |
| File too large | Reject at upload validation |
| Unsupported MIME | Reject at upload validation |

```
├────────────────────────────────────────────────────┤

│  - Personal contract templates                      │
│  - Preferred writing styles                         │
│  - Specialty precedents                             │
├────────────────────────────────────────────────────┤
│ Lawyer B (lawyerId = "user-b")                      │
│  - Different templates                              │
│  - Different style preferences                      │
└────────────────────────────────────────────────────┘
```

### 8.2 Query Filter

All vector searches include:
```sql
WHERE lawyerId = $currentUserId OR lawyerId IS NULL
```

This ensures:
- Lawyers can only see their own + shared knowledge
- Shared knowledge is accessible to everyone
- No cross-lawyer data leakage

## 13. Security Considerations

1. **Data Isolation**: Strict lawyerId metadata filter on all queries
2. **File Upload**: 20MB limit, MIME whitelist (PDF, DOCX, TXT only)
3. **Rate Limiting**: Embedding requests rate-limited (prevent abuse)
4. **Prompt Injection**: RAG context clearly delimited in system prompt
5. **PII Protection**: Content stored in LawKnowledge.content is text -- access controlled via auth
6. **Feature Flags**: All new features default to OFF in production
